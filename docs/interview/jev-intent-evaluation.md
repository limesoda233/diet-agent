# Jev 意图识别与评测链路面试资料

## 一、30 秒项目介绍

这是一个基于 Spring Boot、AgentScope 和 DeepSeek 的多 Agent 饮食推荐系统。我把 Jev 接入到两个低熵、结构明确的决策环节：在线意图与槽位识别，以及离线回答质量评分。在线链路采用 Jev → DeepSeek → Java 规则三级架构，Jev 用结构化问题完成 6 类意图分类和 7 维多值槽位抽取；置信度不足或调用异常时自动回退。评测链路采用确定性规则指标、Jev Judge 和用户反馈的混合评分，并对缺失评分动态归一化，避免外部模型故障中断批量评测。

在 72 条中文标注数据上，本次级联评测的 Accuracy 和 Macro-F1 均为 98.61%。Jev 实际调用 72 次并直接完成 59 次决策，直接路由率为 81.94%；剩余 13 次低置信度请求回退 DeepSeek，Jev 异常和 Java 规则兜底均为 0。

## 二、为什么引入 Jev

原链路把意图识别和槽位抽取全部交给 DeepSeek，让生成式模型输出 JSON。这个方案语义能力强，但存在三个工程问题：

1. 意图分类属于候选集合固定的决策任务，使用生成式模型能力过剩。
2. 自由文本 JSON 需要解析、枚举校验和异常兜底，输出契约不够稳定。
3. 所有请求都调用 DeepSeek，无法根据任务难度分流，延迟和调用成本缺少优化空间。

Jev 更适合候选明确、需要类型化输出的判断任务。设计目标不是完全替换 DeepSeek，而是让 Jev 处理大部分明确请求，让 DeepSeek继续处理低置信度、口语化和长尾表达。

## 三、意图识别链路

~~~mermaid
flowchart TD
    A[用户当前输入] --> B[从数据库加载合法槽位枚举]
    B --> C[Jev System One]
    C --> D[Choice: 6 类意图]
    C --> E[Noul: 7 维槽位候选独立判断]
    D --> F{意图置信度 >= 0.70?}
    E --> F
    F -->|是| G[采用 Jev 意图和槽位]
    F -->|否| H[DeepSeek IntentAgent]
    C -->|超时/HTTP/解析异常| H
    H -->|成功| I[解析 JSON 并过滤非法槽位]
    H -->|失败| J[Java 关键词规则兜底]
    B -->|槽位字典加载失败| J
    G --> K[基于会话状态修正意图]
    I --> K
    J --> K
    K --> L[澄清判断或后续推荐]
~~~

### 1. 动态加载槽位字典

系统先从数据库读取允许的槽位值，包含：

- mealTime：餐次
- mood：情绪
- scene：场景
- healthGoal：健康目标
- cuisine：菜系
- taste：口味
- convenience：便利性

槽位候选由数据库配置驱动，Jev 和 DeepSeek 都不能创建字典之外的标签。这减少了幻觉标签，也允许业务侧修改候选项而不改 Java 枚举。

### 2. 构造 Jev 状态

一次请求携带三类上下文：

- currentMessage：当前用户输入
- knownSlots：会话中已知的槽位
- recentHistory：最近对话摘要和历史意图

历史只用于消解“换一个”“还是太辣”等上下文指代。槽位抽取要求以当前消息为准，避免把历史偏好误判为用户本轮新表达的槽位。

### 3. Choice 完成单意图分类

意图是互斥的主路由，因此使用一个 Choice 问题，从以下 6 类中选择：

- MEAL_RECOMMENDATION
- CLARIFY_NEEDED
- MEAL_ADJUST
- MEAL_PLAN
- HEALTH_RISK
- OTHER

### 4. Noul 完成多值槽位抽取

每一个合法槽位候选生成一个独立的二元概率问题。例如：

~~~text
当前消息是否明确表达了 taste=清淡？
当前消息是否明确表达了 cuisine=川菜？
当前消息是否明确表达了 convenience=快手？
~~~

槽位概率默认达到 0.70 才进入 SlotBundle。多个问题可以同时成立，因此能够表示“晚餐 + 川菜 + 清淡 + 快手”这样的多值结果。

### 5. 置信度门控

Jev 意图置信度默认阈值为 0.70：

- 达到阈值：直接采用 Jev 结果。
- 低于阈值：调用 DeepSeek IntentAgent。
- Jev 超时、HTTP 异常或类型化答案非法：调用 DeepSeek。
- DeepSeek 超时、异常或 JSON 解析失败：使用 Java 关键词规则。

0.70 是初始工程阈值，不代表“70% 置信度就等于 70% 正确率”。阈值需要通过标注数据，在覆盖率、准确率和延迟之间校准。

### 6. 状态修正与澄清

模型决策之后仍执行确定性后处理：

- 健康风险意图优先。
- 没有历史推荐时，“换一个”不能直接进入调整链路，会修正为首次推荐。
- 信息不足时进入澄清流程。
- 本地规则兜底返回 0.2 置信度和空槽位，避免模型失败后继续猜测用户偏好。

## 四、意图链路如何降级

| 场景 | 处理 |
|---|---|
| Jev 未配置或关闭 | 直接调用 DeepSeek |
| Jev 成功但置信度低 | 回退 DeepSeek |
| Jev 超时、HTTP 或解析异常 | 记录原因并回退 DeepSeek |
| DeepSeek 失败 | Java 关键词规则兜底 |
| 槽位字典加载失败 | 不传递不受约束的候选，直接保守规则兜底 |
| 所有模型不可用 | 返回低置信度结果，由澄清链路补充信息 |

这里区分了三种情况：

- 低置信度是业务不确定性。
- 调用异常是基础设施失败。
- Java 规则是最终可用性保障。

系统不会把模型异常伪装成高置信度默认结果。

## 五、可观测性如何证明 Jev 参与

在线链路记录两类 Trace 事件：

- JEV_INTENT_DECISION：Jev 成功返回结构化结果。
- JEV_INTENT_FALLBACK：记录 low_confidence 或具体异常原因。

实时评测还统计：

- Jev 尝试次数
- Jev 直接采纳次数和采纳率
- 低置信度降级次数
- 异常降级次数
- DeepSeek 实际调用次数
- Java 规则兜底次数
- 每条样本的 decisionSource

判断标准：

- Jev attempts > 0：证明 Jev 被真实调用。
- Jev accepted > 0：证明 Jev 结果成为最终 Agent 决策。
- decisionSource=DEEPSEEK：该样本经过模型级降级。
- decisionSource=RULE_FALLBACK：外部模型链路最终失败。

## 六、评测打分链路

~~~mermaid
flowchart TD
    A[读取完整请求 Trace] --> B[计算确定性规则指标]
    A --> C[构造 Judge 证据上下文]
    C --> D[Jev 结构化 Judge]
    D -->|成功| E[解释质量和自然度]
    D -->|异常| F[DeepSeek Judge]
    F -->|成功| E
    F -->|失败| G[Judge 维度缺失]
    B --> H[规则分 60%]
    E --> I[Judge 分 10%]
    G --> J[按现有维度重新归一化]
    K[用户反馈 30%] --> J
    H --> J
    I --> J
    J --> L[最终综合分]
~~~

### 1. 确定性指标优先

系统先从 Trace 计算可以客观判断的指标：

- 意图准确率
- 槽位准确率
- 澄清必要性
- 安全合规
- 幻觉控制
- 多轮一致性
- 延迟
- Token 成本
- 降级率

这些指标不交给模型自由判断，保证结果可复现。

### 2. Judge 使用完整证据

Jev Judge 不只看到最终回复，还会收到：

- 用户原始问题
- 预测意图和槽位
- 是否触发澄清
- 召回候选餐食
- 候选匹配分和知识证据
- 最终回复
- 规则层安全与幻觉检查结果

这样可以判断推荐是否有召回证据支撑，避免只根据语言是否流畅打分。

### 3. Jev 评分问题

一次请求同时评估两个五档序数问题：

- explanation_quality：推荐理由是否准确、有证据且解释充分
- naturalness：表达是否自然、清晰、符合对话场景

Jev 的 0～4 分转换为系统原有的 1～5 分，保持与历史 DeepSeek Judge 数据兼容。

### 4. Judge 降级

- Jev Judge 成功：使用 Jev 分数。
- Jev Judge 异常：回退 DeepSeek Judge。
- 两个 Judge 都失败：返回空 Judge 结果，批量评测继续。
- 聚合时移除缺失维度，对剩余权重重新归一化，而不是把 Judge 记为 0 分。

默认权重为规则 60%、Judge 10%、用户反馈 30%。这种设计避免外部评分服务故障错误拉低业务质量分。

## 七、使用 Jev 前后的实测对比

同一套 72 条中文意图数据：

| 指标 | DeepSeek 历史基线 | Jev–DeepSeek 级联 | 变化 |
|---|---:|---:|---:|
| 最终 Accuracy | 97.22% | 98.61% | +1.39 个百分点 |
| 最终 Macro-F1 | 97.22% | 98.61% | +1.39 个百分点 |
| DeepSeek 调用率 | 100% | 18.06% | -81.94 个百分点 |
| Jev 直接路由率 | 0% | 81.94% | +81.94 个百分点 |
| P50 延迟 | 892 ms | 811 ms | 约下降 9.1% |
| P95 延迟 | 1227 ms | 2169 ms | 约上升 76.8% |
| Jev 异常 | 不适用 | 0 | 无异常 |
| Java 规则兜底 | 未单独对比 | 0 | 本轮未触发 |

本次级联的内部表现：

| 决策来源 | 样本数 | 准确率 | P50 | P95 |
|---|---:|---:|---:|---:|
| Jev | 59 | 98.31% | 736 ms | 1857 ms |
| DeepSeek 降级 | 13 | 100% | 1341 ms | 8062 ms |

正确的结论是：

1. Jev 承接了 81.94% 的最终决策，DeepSeek 调用量明显下降。
2. 本轮准确率略高，但样本只有 72 条且模型具有随机性，不能直接宣称 Jev 必然提升 1.39 个百分点。
3. 总体 P50 有所下降，说明主流请求更快。
4. P95 反而上升，因为低置信度样本先等待 Jev，再串行调用 DeepSeek；其中存在 8062 ms 的长尾样本。
5. DeepSeek 调用下降不等于总成本已经下降。真实成本还需要结合 Jev 单价、请求问题数量和重试情况计算。

面试中主动说明 P95 问题会比只讲漂亮数字更可信。下一步可以采用更短的 Jev 超时、按输入风险预路由、熔断器，或者只对高风险长尾请求使用并行 hedging，控制串行降级的尾延迟。

## 八、唯一错误样本怎么分析

~~~text
输入：推荐
预期：CLARIFY_NEEDED
实际：MEAL_RECOMMENDATION
来源：JEV
置信度：0.93
~~~

它说明置信度阈值不能解决所有错误：错误结果也可能高置信。

合理改进包括：

- 增加“极短输入且没有任何槽位”的确定性澄清规则。
- 在 Jev 意图标准中补充短文本 hard negative。
- 扩充短文本和否定表达切片。
- 评估置信度校准，而不仅看 Accuracy。
- 不为了把 72 条数据刷到 100% 而只针对单条样本硬编码。

## 九、面试时的 2 分钟讲法

我原来的意图识别全部由 DeepSeek 完成，让生成式模型返回 intent、slots 和 confidence。这个方案语义能力强，但对于固定候选的分类任务成本偏高，而且自由 JSON 存在解析失败风险。

改造后，我把 Jev 放在第一层。每次请求先从数据库加载七个维度的合法槽位，随后把当前消息、已知槽位和最近历史组成状态。意图用一个 Choice 从六类中单选；槽位用多个独立的 Noul 概率问题抽取，因此可以同时识别晚餐、川菜、清淡和快手等多个条件。

当 Jev 置信度达到 0.70 时直接采用；低置信度、超时或者类型化答案异常时回退 DeepSeek；DeepSeek 再失败才进入 Java 关键词规则。模型结果之后还会结合会话状态修正意图并判断是否需要澄清。

我没有只看最终准确率，而是增加了路由可观测性。在 72 条标注数据上，Jev 实际处理并直接完成 59 条，路由率 81.94%；13 条低置信度请求回退 DeepSeek，最终 Accuracy 和 Macro-F1 都是 98.61%，外部模型异常和规则兜底都是 0。

评测侧采用规则指标加结构化 Judge。安全、延迟、成本和一致性等客观指标由规则计算；解释质量和自然度交给 Jev，并把用户问题、召回候选和知识证据一起提供给 Judge。Jev 失败时回退 DeepSeek，两个 Judge 都失败时跳过该维度并重新归一化权重，所以评测不会因为外部服务故障中断。

这个方案当前的主要问题是尾延迟：低置信度请求会串行调用两个服务，因此 P95 比历史基线高。下一步会通过阈值校准、短超时、预路由和有限 hedging 优化。

## 十、高频追问与回答

### 为什么不直接用 Jev 完全替换 DeepSeek？

Jev 适合候选集合明确的结构化判断，DeepSeek 对隐含语义、模糊口语和长尾表达更有优势。级联架构能逐步迁移并控制风险，也能用真实数据决定哪些流量适合交给 Jev。

### 为什么意图用 Choice，槽位用多个 Noul？

意图是单一主路由，天然互斥；槽位可以多值并存。把槽位做成多个独立判断，比一个大 Choice 更符合数据结构，也能直接使用概率阈值过滤弱证据。

### 0.70 阈值怎么确定？

当前是初始值。正式做法是在开发集上绘制阈值与覆盖率、准确率、DeepSeek 调用率、P95 延迟之间的关系，再选择满足业务约束的点，最后在冻结测试集验证。

### 如何证明不是“配了 Key 但没用”？

报告读取真实 Trace 调用：Jev 成功返回才产生 JEV_INTENT_DECISION，发生降级会产生 JEV_INTENT_FALLBACK，DeepSeek 通过实际 IntentAgent 调用计数。当前数据是 Jev 尝试 72、采纳 59、DeepSeek 调用 13。

### 为什么 P95 变差？

13 个低置信度请求串行经历 Jev 和 DeepSeek，尾部延迟会叠加。其中有一条达到 8062 ms。可以缩短第一层超时、识别高风险输入后直接路由 DeepSeek，或对少量长尾请求做 hedged request。

### 如何控制槽位幻觉？

槽位选项来自数据库。Jev 只能回答已生成的候选问题；DeepSeek 的输出也会经过 SlotJsonPicker 过滤，数据库之外的值不能进入 SlotBundle。

### Judge 会不会自说自话？

Judge 只承担解释质量和自然度等主观维度，并且输入包含原始问题、候选餐食和知识证据。安全、准确率和延迟等指标由确定性代码计算，不由 Judge 决定。

### 两个外部服务都挂了怎么办？

在线意图链路进入 Java 规则并返回低置信度结果，再由澄清流程补充信息。离线 Judge 返回空值，评分按仍然存在的规则分和用户反馈重新归一化，批任务继续执行。

## 十一、简历表达

### 精简版

在 Spring Boot 饮食推荐 Agent 中设计 Jev–DeepSeek 级联意图识别链路，使用 Choice 与 Noul 完成 6 类意图决策及 7 维多值槽位抽取，并通过置信度门控、异常降级和 Java 规则兜底保障可用性。

### 数据版

基于 72 条中文标注数据构建可观测评测体系，Jev 直接承接 81.94% 请求，剩余低置信度请求自动回退 DeepSeek；最终 Accuracy 与 Macro-F1 均达 98.61%，健康风险召回率 100%，Jev 异常和规则兜底均为 0。

### 评测版

构建规则指标、Jev 结构化 Judge 与用户反馈融合的质量评测链路，将原始请求、召回候选和知识证据纳入评分上下文；Jev 异常自动回退 DeepSeek，双模型失败时按可用维度重新归一化，保证批量评测不中断。

## 十二、表达边界

面试和简历中不要声称：

- Jev 准确率是 100%。
- Jev 让 P95 延迟下降。
- DeepSeek 调用下降就等于总成本下降。
- 72 条离线数据等于线上真实用户效果。
- 评测 Judge 的准确性已经通过人工一致性实验。

更准确的说法是：当前完成了工程链路和离线标注集验证；路由覆盖率、准确率和降级行为已经可观测，成本、Judge 一致性和线上效果仍需要扩大样本和重复实验。
