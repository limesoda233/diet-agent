# 一句话录入个人餐食：页面与聊天共用草稿

日期：2026-10-11。状态：工程验收完成；真实模型提取质量待抽查，见 [验收记录](acceptance.md)。

## 用户已确认的决策

- 两个入口：个人餐食管理页，以及聊天窗口。
- 聊天只有明确要求“录入／保存到我的餐食库”才进入录入流程；“中午吃了宫保鸡丁”等普通描述不触发，也不主动提示保存。
- 先生成可编辑草稿，确认后才创建个人餐食。
- AI 将口语整理为结构化数据，代码负责字段、标签和保存校验。

## 目标与边界

减少逐项选择标签的操作，沿用现有个人餐食 MySQL 存储。当前保存条件为菜名非空、餐次至少一项；mood、scene、healthGoal、cuisine、taste、convenience 可留空。

首版支持单道餐食新增，不自动覆盖已有餐食；同名遵循原新增规则。一次描述包含多道菜时提示拆成单条录入。既有人工新增、编辑、删除继续可用。不新增文档上传、MinerU、公共 RAG 导入或批量处理。

## 共用数据流程

口语描述 → 轻量模型提取 → 代码规范化／校验 → 餐食草稿 → 用户补充或修改 → 明确确认 → 复用 MealService 保存到个人库。

提取模型复用现有 AgentScope 轻量聊天模型配置，不使用 embedding、视频 MCP 或菜谱 Answer Agent 做录入。模型只产出结构化结果，不拥有数据库写工具；用户身份、个人来源类型和数据库 ID 由后端决定。

每个入口共用同一提取、校验和草稿数据契约，不能各自维护一套 Prompt 或标签映射。

## 提取与校验约定

- 输出菜名和现有七类标签；标签候选来自 `SlotOptionService` 当前启用词表，接受“中午”到“午餐”等规范化。
- 每个非空提取字段附带用户原文依据，后端核对该片段确实存在于本次描述或明确补充中；这只证明提取可追溯，不宣称所有语义推断都正确，预览确认仍不可省略。
- 仅提取用户明确提供的信息。未提到的可选标签留空，不因宫保鸡丁常见于川菜就自动加菜系，也不根据菜名断言营养价值。
- 可保存用户明确提供的食材、描述和简略做法到 `meal_knowledge`，来源固定为 `USER_PROVIDED`；没有说做法就留空，不扩写完整菜谱。
- 草稿保留原始描述，展示缺少字段与校验提示。模型返回未知标签、无依据字段或无效 JSON 时，不将该输出直接交给保存接口；错误信息可重试，人工录入仍可用。
- 必填项缺失时允许返回草稿，但禁止确认保存。不得自动猜餐次、把全部餐次填满或自动起一个推测菜名来绕过校验。
- AI 不能提供 ownerUserId、sourceType、mealId 等控制字段。保存时再次执行原 MealService 校验，不信任前端“已校验”的状态。
- 当前选中菜品能明确确定时，可以作为用户显式指代的菜名依据；指代不明确就问菜名，不猜测任意历史消息，也不自动复制公共菜谱到个人做法。

示例：

| 输入 | 草稿 |
| --- | --- |
| “食堂的宫保鸡丁，中午吃，微辣，里面有鸡肉和花生” | 菜名宫保鸡丁、午餐、微辣、鸡肉／花生；其它未提标签留空 |
| “帮我录入番茄鸡蛋面” | 菜名番茄鸡蛋面；缺少餐次，需要补充 |
| “有鸡肉和花生，帮我录入一份餐食” | 不自动命名宫保鸡丁，提示缺少菜名和餐次 |

## 管理页交互

在新增餐食区域增加口语输入框和“AI 整理”按钮，生成后回填现有标签表单，并展示可编辑的描述、食材与做法。用户仍可完全手动填写。

生成草稿不创建 `meal_item` 或 `meal_knowledge`。缺菜名／餐次时明确标注，用户补齐后点击原保存入口。生成和保存期间禁用相应按钮，失败恢复操作并保留输入；成功刷新个人餐食列表。

提取接口拟为 `POST /api/v1/diet/meals/personal/draft`，请求提供口语 `text`，返回草稿、缺失字段、提示和解析状态。管理页草稿留在前端，实际保存复用 `POST /api/v1/diet/meals/personal`；不宣称该旧新增接口具备跨请求的严格幂等能力。

## 聊天交互与状态

1. 明确录入请求在普通推荐／菜谱分发前进入独立草稿流程，包含“食材、做法”的录入描述不能误走 RAG。
2. 输出餐食草稿卡，显示提取结果和缺失项；缺菜名或餐次时提出具体问题。仅在待补字段状态接受对应短回复，其它问答仍走原业务链路。
3. 用户可明确补充／修改草稿字段；只更新提到的字段，保留其他已确认内容。通用“是／好”不代表保存。
4. 完整草稿显示“确认保存”和“取消录入”。按钮使用当前 sessionId 和 draftId 发起明确动作；明确的“确认保存”文本也仅在当前存在一份完整草稿时成立。
5. 保存校验当前用户、当前草稿 ID 和状态，拒绝过期或不属于当前会话的动作；即使聊天数据源选择 PUBLIC，新录入也只能写入当前用户 PERSONAL 库。
6. 成功返回餐食 ID 与已保存提示，刷新个人库；取消清理待录入状态，不创建餐食。

草稿状态为 `NEEDS_INPUT`、`READY`、`SAVED`、`CANCELLED`。会话草稿和保存回执放入现有 `diet_sessions.slots._meta`，与推荐七槽位及菜谱指代状态分开；旧会话缺字段时默认为无草稿，无需新增表。

保留同一 session 的串行处理，并在锁内读取用于草稿动作的最新状态，避免排队请求使用锁外旧快照。聊天保存将餐食创建与草稿回执更新纳入同一数据库事务；已保存的同一 draftId 返回原回执，不能因重复点击再创建一条。此保证限定于当前单实例部署，不宣称多实例分布式锁能力。

草稿响应在 ChatResponse 中增加可选的结构化草稿数据，旧响应保持兼容。草稿卡不复用 MySQL 推荐的 displayBlocks，避免改变推荐展示快照和“换一批”历史。

## 工程与运行约定

- 原始口语输入上限 4000 字符，模型调用默认超时 10 秒、单次尝试，可通过项目配置调整。模型失败、无有效提取结果或无合法餐次时，展示错误或缺失项，不伪造成功。
- 记录草稿生成、澄清、确认、取消与保存终态，能定位入口、校验问题、解析耗时和保存结果；不在日志中输出 API Key 等凭据。
- 页面切换用户、重新生成草稿或取消时清理旧草稿可执行状态，旧卡片不得保存到新用户库。
- 不改变 MySQL 推荐数据域，不写入 Lucene/Qdrant，不新增本地数据库密码或云 API 凭据。

## 验收标准

| ID | 验收 |
| --- | --- |
| MI-01 | 两入口对同一口语描述使用相同提取／校验流程，得到相同有效字段 |
| MI-02 | 普通“中午吃了宫保鸡丁”、食材问答和菜谱问答不触发录入、不写库 |
| MI-03 | 明确录入请求生成草稿，生成阶段不创建餐食；出现“做法”等词不误走 RAG |
| MI-04 | 菜名和餐次缺失时不能保存；聊天可补字段、管理页可手动补齐，其余标签可空 |
| MI-05 | 未提信息不自动填充，未知标签／非法字段／模型失败不绕过后端校验，不扩写做法或营养事实 |
| MI-06 | 用户确认后只创建当前用户 PERSONAL 餐食；提供的知识使用 USER_PROVIDED 来源，不进入公共索引 |
| MI-07 | 聊天重复确认、过期草稿、取消及跨用户动作不能重复或错误创建餐食；会话重载保留草稿与回执 |
| MI-08 | 保存失败不遗留半完成餐食或虚假保存回执，可保留草稿重试；管理页防重复点击 |
| MI-09 | 老会话默认无草稿；新增草稿不污染推荐槽位、展示顺序、菜谱选择和已有人工 CRUD |
| MI-10 | 两入口能完成完整操作，页面成功刷新列表，Trace 区分生成成功与保存成功 |

先补离线失败用例，再实现提取／校验服务、页面入口、聊天状态与确认动作。外部模型使用受控替身测试；事务行为和前端交互各自验证，真实模型抽查另行记录。交付前执行 `mvn test`、`mvn -DskipTests package`，冻结测试集不参与此功能调参。
