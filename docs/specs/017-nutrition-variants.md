# 餐食搭配版本与营养估算

## 目标

一道餐食可保存多个常吃搭配版本。录入时保留现有餐食标签，针对麻辣烫等可变餐食展示有限的份量、组成、汤底与调味按钮。用户明确描述优先，AI 只预选允许的选项。用户确认后，服务端按版本化参考规则计算每份热量和营养区间。推荐可在用户提出控碳水、减脂或高蛋白目标时参考有估算依据的版本。

## 边界

- 营养选项可跳过；无足够信息时不显示数值，也不能当作低热量餐食排序。
- 份量、蔬菜、肉/豆制品、主食、用油、麻酱、白糖、辣度均为按钮，默认由菜名和原话预选。用户明确说“不加辣”“不要麻酱”等条件不得被 AI 建议覆盖。
- 服务端根据餐食名称匹配已支持的模板，AI 只预选模板内的选项；计算由服务端固定算法完成。估算保存区间、假设和算法版本；不能表达为测量值或医疗建议。
- 同名餐食沿用现有合并规则；搭配版本归属餐食，同名不同搭配保留多个版本。
- 公共餐食仅能由管理流程写入，个人版本由本人访问和修改；不把个人数据写入公共库或 RAG。
- “想吃辣的”是宽泛检索，覆盖微辣、中辣、重辣和麻辣；“微辣”仍是具体辣度，“不辣”不能算作辣味命中。

## 当前实现与验证

- 规则问卷目前覆盖麻辣烫/冒菜和炸串/串串；普通餐食继续使用原标签，不显示无依据的热量数字。公共库增补麻辣烫、炸串两类参考餐食；其展示区间按默认搭配计算。
- 用户可在小程序手动录入与聊天草稿、React 手动录入与聊天草稿中调整标签和搭配；个人餐食可保留多份不同搭配，改名跨模板时旧搭配清除。
- `mvn test`、`npm --prefix frontend test`、`npm --prefix miniapp test` 已本地通过；云端真实模型建议、MySQL 迁移和真机交互仍需上线后验收。估算规则是宽区间经验模型，未针对商家、配方或个人实际食量校准。

## 实施顺序

1. 为餐食版本建表和受约束的数据模型，写估算规则测试；重点覆盖份量、配料和调味变化及不确定输入。
2. 增加 AI 预选与服务器校验，写用户明确条件优先的测试；模型失败时返回可手动选的默认模板。
3. 接入个人餐食创建、同名合并、版本查询和修改；验证用户隔离、事务与旧餐食兼容。
4. 在小程序录入页和聊天草稿、React 录入页增加按钮与估算预览；默认不要求填写营养信息。
5. 推荐链路对营养目标使用有版本数据的候选，展示选用的版本与区间；无数据时不作营养声称。
6. 执行 Java、React、小程序测试与打包，记录云库迁移和部署步骤。
