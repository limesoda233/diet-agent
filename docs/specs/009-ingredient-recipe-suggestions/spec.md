# 按食材找菜的回答优化

日期：2026-10-11。状态：工程验收完成；真实模型回答质量待抽查，见 [验收记录](acceptance.md)。

## 问题与目标

用户问“冰箱里有鸡腿肉丁、花生米、辣椒、大葱，能做什么菜”时，当前 RAG 能召回并输出宫保鸡丁菜谱，但回答直接进入食材与步骤，没有解释为什么选这道菜、用户还需要准备什么。

本阶段在公共菜谱问答中补充选菜说明。回答中的菜名、匹配关系、缺少原料和步骤都必须有本轮证据依据；不把检索相似度当作“食材齐全”或“健康适合”的证明。

## 已确定边界

- 餐食标签推荐继续使用 MySQL；按食材寻找公共做法使用菜谱 RAG。
- HowToCook 来源版本、父子分块、BM25/dense 并行、RRF 和父菜谱恢复沿用现有实现。
- 不新增公共语料，不修改锁定 test 的 queries/qrels，不将个人餐食写入公共索引。
- 复用现有 RecipeAnswerAgent，在一次回答生成中完成推荐说明和菜谱，不增加单独的推荐 LLM 调用。
- 查询改写、重排和视频启用规则沿用当前配置，不将可选能力改为默认开启。
- 现有菜谱与视频并行流程保留。此阶段不以生成后的推荐理由作为视频搜索前置条件。

## 用户行为

区分两种回答目的，仍属于菜谱业务域：

| 用户问题 | 回答形式 |
| --- | --- |
| “宫保鸡丁怎么做”“第三道怎么做” | 指定菜的食材、步骤和引用 |
| “这些食材能做什么菜”“有鸡肉和花生，可以做哪些菜” | 先推荐说明，再展示首选菜谱；其它有证据的候选可简述 |

识别按食材找菜的常见问法，避免仅靠“怎么做”关键词才能进入菜谱链路。明确的个人录入请求优先交给阶段 010，不能因为描述中出现“做法”就误走 RAG。

用户可用食材不等于 `requiredIngredients`：不要求每个推荐菜都使用所有食材，也不凭空假定用户有盐、油、酱油等调味料。“只有这些”“不要某食材”等条件保留在完整问题中；回答证据不足或条件冲突时说明限制。此阶段不新增完整的食材实体本体或严格库存求解器。

## 回答约定

1. 开头直接回答可优先考虑哪道菜，并引用本轮菜谱。
2. 解释用户提供的主要食材与原文有什么对应关系；生花生和熟花生、鲜辣椒和干辣椒等不自动视为完全相同。
3. 对原文要求、用户未说明持有的原料表述为“还需确认／准备”，避免断言用户一定没有。用户已明确缺少且原文没有替代方案时，不编造替代方案。
4. 接续首选菜谱标题、食材列表、步骤列表与来源引用，保留当前 Markdown 渲染和视频卡片。
5. 只展示有本轮证据的候选，不为了凑数量编菜名，不根据名称或食材自行下低脂、低油等营养结论。
6. 回答生成使用完整问题；改写后的文本只用于检索，不能导致回答忘记“只有”“不要”等条件。
7. 模型明确拒答时尊重拒答。模型异常或 JSON/引用校验失败时，现有确定性回退也应保留“根据本轮检索可考虑该菜”的说明；无法可靠核对食材时明示需核对原料，不伪造具体匹配结论。

文字形式示意（正式输出的菜名和引用取自本轮证据）：

> 可以优先考虑宫保鸡丁。你提供的主要食材与该菜谱较接近，但仍需核对辣椒、花生的处理状态，以及原文要求的调味料。[S1]
>
> 接下来列出这道菜的原文食材、步骤与来源。

## 代码职责

- 菜谱路由／查询准备：识别回答目的，并保留原始食材问题。
- 证据回答层：依据目的组织 Prompt；沿用本轮引用检查，确定性回退保持相同回答目的。
- 编排与前端：沿用 Markdown 与视频卡片，不新增 MySQL 推荐的前置依赖。
- Trace：能够查看回答目的、实际检索问题、生成方式和分支终态。
