# 013 菜谱重排与相关性筛选

日期：2026-10-19。用户已确认采用专用 Cross-Encoder、云 Rerank API、开发集校准和显式失败降级。

## 范围与契约

- 仅修改公共菜谱链路，不改 MySQL 推荐、个人做法、既有 query/qrels。
- 默认仍使用 identity；显式开启 `diet.recipe-rag.rerank.enabled` 才创建真实重排器。
- 接入 SiliconFlow/Cohere 风格的文本 `/rerank` 契约：model、query、documents、top_n、return_documents=false；响应使用 index 和 relevance_score，禁止服务端返回正文替换本地文档。
- 基线模型 `BAAI/bge-reranker-v2-m3`，endpoint/model/key/timeout 可配置，密钥不进入 Trace、错误、报告或版本控制。
- 两路各 20 子块不变；开启时融合后保留最多 20 道父候选，重排筛选后最多 3 道进入回答。关闭时保留现有 final-top-k 行为。
- 重排使用指代已解析、改写前的完整用户问题；候选按菜名、别名、食材、步骤组织，单候选字符预算默认 3000，并记录文本指纹供复现。
- 请求一次返回所有送入候选的分数。索引必须完整、唯一、在范围内，分数必须是有限数；空响应、重复索引、漏项、非法 JSON 均视为评分失败。RRF 与重排分数分开记录。
- `filter-enabled=true` 时必须显式设置有限的 `min-score`，不提供默认有效阈值；分数不解释为相关概率。仅重排对照可关闭过滤。
- 输出区分 BYPASSED、ACCEPTED、FILTERED、UNAVAILABLE。过滤后空结果不调用回答模型；服务故障不使用未过滤候选生成答案，不自动重试；视频分支独立保留。
- 本阶段不实现自然语言食材硬约束解析或检索前 metadata 过滤，不宣称重排能验证营养事实。

| REL-01 | 默认关闭无外部连接；开启缺 key/endpoint/模型/有效预算等配置时明确失败，开启过滤缺阈值时启动失败 |

## 实施顺序

1. 结构化结果、HTTP 评分与配置：先写 HTTP fixture 和配置测试，再实现。
2. 接入候选预算与服务编排：先写拒答/故障/视频保留测试，再实现。
3. 三组离线对照与运行文档：固定数据不变，先测试统计与冻结保护，再实现 opt-in 入口。
4. 全量验证、代码审查、验收记录；不以模拟分数宣称真实模型收益。
