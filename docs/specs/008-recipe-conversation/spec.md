# 多轮菜谱指代修复

日期：2026-10-10。用户确认修复“推荐菜品后追问怎么做”的多轮链路。

## 行为与存储

- 保存最近实际展示的菜品名称、ID 与顺序；独立于累积推荐排除 ID。
- “怎么做/这道菜怎么做/需要什么食材”等省略菜名的请求，优先使用当前选中菜品，其次使用唯一展示菜品。
- “第二道怎么做”按最近展示顺序确定菜名；越界不猜测。
- 多个候选且没有明确选中对象时先追问；无上下文时询问菜名。追问期间不调用 RAG 或视频。
- 追问后可回复候选菜名或序号，再继续菜谱流程。
- 明确新菜名优先于旧选择；新推荐覆盖展示列表并清除旧选择。
- 解析得到的完整问题在检索前生成，供 RAG 与视频使用；Trace 增加 `RECIPE_REFERENCE_RESOLVED`。
- 状态写入现有 `diet_sessions.slots._meta.recipeConversation`；旧会话默认空上下文，无需建表。
- 个人餐食显式 `mealId` 仍走现有归属校验与个人做法逻辑；从公共推荐解析出的 ID 不当作个人 ID 查询。

## 边界

采用确定性指代解析，不新增 LLM 调用。当前覆盖单菜、序号和候选完整菜名；复杂指代例如“刚才那个鸡肉菜”仍需后续设计。旧会话不从累积排除列表猜出最后展示顺序，更新应用后需要重新推荐一次。

## 验收

验证真实编排和会话 JSON 保存/重载下的推荐后追问、单选、多选、越界、追问选择与继续追问；保留原菜谱、MCP 和 MySQL 推荐测试。交付前执行 `mvn test` 与 `mvn -DskipTests package`。
